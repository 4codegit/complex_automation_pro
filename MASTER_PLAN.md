# ГЕНЕРАЛЬНЫЙ ПЛАН АВТОМАТИЗАЦИИ ОБОГАТИТЕЛЬНОЙ ФАБРИКИ (ПРИКАЗ ДИРЕКТОРА)

> Управляющий документ для всех подразделений. Читается вместе с
> [SENSOR_CATALOGUE.md](SENSOR_CATALOGUE.md) (инженерный реестр сигналов),
> [TZ_DEVELOPMENT.md](TZ_DEVELOPMENT.md) (техзадание разработчикам),
> [TECHNICAL_SPECIFICATION.md](TECHNICAL_SPECIFICATION.md) и
> [ARCHITECTURE_DECISIONS.md](ARCHITECTURE_DECISIONS.md).

## 1. Приказ и назначение

Автоматизировать и оснастить датчиками **весь технологический маршрут** фабрики —
от приёма руды, дробления, измельчения, флотации, сгущения, фильтрации (пресс-фильтр),
сушки — до готового концентрата и отгрузки. Построить систему мониторинга и контроля
качества на всех участках, с чёткими API в обе стороны:

- **PUSH** — устройства/шлюзы толкают показания на сервер;
- **PULL** — сервер отдаёт историю, агрегаты и отчёты по запросу.

Система должна **универсально поддерживать любое количество датчиков** любого типа:
датчик подключается через реестр тегов + адаптер протокола, без переписывания кода.

Система — это бесплатный аналог SCADA уровня мониторинга (Level 3, ISA-95).
**Производство не должно останавливаться из-за CAP.** Система наблюдающая, а не
управляющая; потеря или компрометация CAP не должна остановить или дестабилизировать завод.

## 2. Целевая система (что строим)

| Слой | Состав |
| --- | --- |
| Уровень 0–2 (поле) | Датчики, приводы, PLC/DCS, защиты — **остаются независимыми** |
| Уровень 3 (CAP) | Edge-шлюзы, приём телеметрии, историк, реестр тегов, алермы, мониторинг, отчёты |
| Уровень 4 | ERP, лабораторная система (LIMS), аналитика |

Ключевые свойства:

- **Независимость от производителя датчиков** — адаптеры OPC UA, Modbus TCP, MQTT Sparkplug B, файловый/LIMS API.
- **Единый канонический контракт** телеметрии для всех транспортных протоколов.
- **Буферизация на границе** (store-and-forward): при потере связи шлюз копит данные, при восстановлении досылает.
- **Качество данных**: коды качества `good/uncertain/bad/stale/substituted/offline`, никакой тихой подмены плохих данных нормальными.
- **Профили руды**: настройка параметров под тип руды — версионируется, согласуется, с аудитом.
- **RBAC и аудит**: операторы, металлурги, ОТ-инженеры, директор; каждое изменение — в журнале.

## 4. Универсальный датчик: одна абстракция — много датчиков

Правило: **код не пишется под конкретный датчик**. Любой датчик — это:

1. запись в **реестре тегов** (id, оборудование, имя, единица, тип данных, инженерный диапазон, период опроса, критичность, дата поверки, уставки алермов);
2. **адаптер протокола** (OPC UA / Modbus / MQTT / LIMS-файл), который переводит показание в **каноническое сообщение**;
3. **каноническое сообщение** — единый JSON для всех транспортов.

Добавление нового датчика = регистрация тега (+ при необходимости — новый драйвер).
Один и тот же конвейер приёма данных обслуживает тысячи тегов разных типов и единиц.

## 5. Push и Pull — обе модели

**Push (основная, для живых данных):**
- шлюз/устройство отправляет показания по мере появления: OPC UA (Pub/Sub), MQTT Sparkplug B, Modbus-клиент, REST `POST /ingest/telemetry` и `:batch`;
- при потере связи шлюз **копит локально**, при восстановлении досылает с сохранением `message_id` (идемпотентность);
- сервер отвечает по каждому сообщению: `accepted` / `duplicate` / `rejected(code)` — шлюз удаляет только принятые/дубликаты.

**Pull (для запросов и редких данных):**
- история и агрегаты: `GET /telemetry`, `GET /telemetry/latest`, `GET /telemetry/aggregates`;
- управляемый backfill шлюза после разрыва (шлюз спрашивает сервер, чего не хватает);
- отчёты и корреляция с лабораторией;
- если устройство не умеет push — адаптер-поллер сам опрашивает устройство (это внутри шлюза, не сервера).

**Запрет:** push/pull никогда не используются для команд в поле. Управление — только через штатные PLC/DCS и процедуры.

## 6. Профили руды: настройка под тип руды

Настройки зависят от типа руды (сульфидная медь, золото-сульфидная, железная,
полиметаллическая, окисленная/глинистая и т.д.). Профиль версионирует:

- домен руды, минералогию, вредные компоненты;
- содержание металла в питании, крепость (индекс Бонда / work index), влажность, засорённость глиной, гранулометрию;
- целевые параметры: крупность помола P80, плотность пульпы, pH, схема реагентов, целевой сорт концентрата, извлечение, производительность;
- разрешённый рабочий коридор, уставки алермов, ссылки на технологический регламент;
- входные данные лаборатории и сверка баланса (reconciliation).

Изменение профиля — только по согласованию (роль + комментарий + аудит). Примеры
параметров по типам руд — в [SENSOR_CATALOGUE.md](SENSOR_CATALOGUE.md), раздел «Профили руды».

## 7. KPI

**KPI завода (которые система должна сделать видимыми):**
- извлечение металла (металлургический баланс);
- сорт концентрата;
- влажность концентрата (норма по контракту);
- производительность (т/ч), коэффициент использования;
- удельный расход реагентов, воды, энергии;
- простой и состояние оборудования (оборудование-дерево, condition monitoring).

**KPI проекта — ворота качества** (см. раздел 8): каждый этап принимается по
документированным критериям, иначе — не двигаемся дальше.

## 8. Фазы внедрения и ворота качества (phase gates)

| Фаза | Содержание | Ворота (критерий приёмки) |
| --- | --- | --- |
| 0. Discovery | обход завода, P&ID, реестр тегов/приборов, сетевые зоны, матрица ответственности, шаблон профиля руды, alarm philosophy | утверждены границы объёма и read-only граница |
| 1. Фундамент | локальное окружение, API-контракт, реестр активов/тегов, симулятор, автотесты, наблюдаемость, threat model | контрактные тесты и тесты отказа проходят |
| 2. Edge-пилот | один некритичный участок: адаптер, буферизация, коды качества, историк, дашборд | данные сверены с приборами; восстановление после обрыва принято эксплуатацией |
| 3. Мониторинг-пилот | тренды, алермы, корреляция с лабораторией, RBAC | рационализация алермов и приёмка операторами |
| 4. Масштабирование | все участки, резервирование, бэкап/восстановление, нагрузочные и защитные тесты | ревью готовности к продакшену |
| 5. Прод | FAT/SAT на площадке, ранбуки, план отката, реакция на инциденты | go/no-go директора |

## 10. Продуктовая стратегия (CAP как бизнес)

Система проектируется **конфигурируемой под другую фабрику / тип руды**, поэтому после
внедрения на нашей фабрике она предлагается другим предприятиям:

- реестр тегов и профили руды — данные, а не код (перенос = настройка, не разработка);
- библиотека адаптеров (OPC UA / Modbus / MQTT / LIMS) — переиспользуемая;
- бренд и лицензия: on-prem либо управляемая установка; подписка на обновления и поддержку;
- пакет «под ключ»: обход площадки → каталог сигналов → развёртывание → обучение операторов.

## 11. Что нельзя (жёсткие правила безопасности)

- Никакого пути «интернет → PLC/DCS/SIS» и общих учётных записей IT/OT.
- Никакого управления полевым оборудованием из CAP (без отдельно санкционированного проекта с HAZOP, доступом, аудитом и приёмкой).
- Никаких «жёстко зашитых» универсальных уставок — только согласованные профили.
- Никакой тихой замены `bad/stale` значений нормальными.
- Никакого симулятора в продакшене (`SIMULATOR_ENABLED=false`).
- Потеря связи/дефект CAP не останавливает производство.
