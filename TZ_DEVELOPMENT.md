# ТЕХНИЧЕСКОЕ ЗАДАНИЕ ДЛЯ ГРУППЫ РАЗРАБОТКИ (CAP)

> Исполнителям: группа разработки (бэкенд, фронтенд, edge-шлюзы, ОТ-интеграция).
> Основание: приказ директора — [MASTER_PLAN.md](MASTER_PLAN.md).
> Инженерные данные: [SENSOR_CATALOGUE.md](SENSOR_CATALOGUE.md).
> Существующие решения и границы: [TECHNICAL_SPECIFICATION.md](TECHNICAL_SPECIFICATION.md),
> [ARCHITECTURE_DECISIONS.md](ARCHITECTURE_DECISIONS.md).

## 1. Цель и границы

Развернуть отлаженный **Level 3**-мониторинг всего технологического маршрута: приём
руды → дробление → измельчение → флотация → сгущение → пресс-фильтр → сушка →
готовый концентрат → отгрузка. Универсальная поддержка датчиков (любое количество,
любых типов), PUSH и PULL API, мониторинг/дашборд, алермы, профили руды, RBAC и аудит.

**Жёсткая граница:** система read-only для поля. Без команд в PLC/DCS/SIS/привода.
Потеря/компрометация CAP не останавливает производство.

## 2. Текущее состояние (аудит, сделано)

- FastAPI + SQLAlchemy(async) + asyncpg; Redis (pub/sub → WebSocket); React/Vite (dashboard).
- Реестр Asset/Tag (8 демо-тегов), приём `POST /ingest/telemetry` и `:batch` с идемпотентностью по `(gateway_id, message_id)`, коды качества, `GET /telemetry`, `GET /telemetry/latest`, `GET /assets`, `GET /tags`, `GET /health`, `/simulator/*`, `/alerts`.
- Тесты 8 шт. зелёные (SQLite in-memory), контракт согласован в `backend/API.md`.
- **Разрыв с целевой архитектурой (важно):** историк = таблица в PostgreSQL (без агрегаций по времени и retention), нет схемы для булевых/строк/структур, нет `sent_at`, нет профилей руды, нет алермов с состояниями и ack, нет RBAC, нет шлюзов/адаптеров, нет backfill, нет аудита, симулятор публикует не по каноническому контракту в базу, уставки «зашиты» в `schemas.py`, а не в профили.

## 3. Целевая архитектура

```
[Поле: датчики/PLC/DCS]  (уровни 0–2, вне CAP)
        │  OPC UA / Modbus TCP / MQTT Sparkplug B / файл(LIMS)
        ▼
[Edge Gateway (Go)]   ── протокольные адаптеры, нормализация в каноническое
        │  сообщение, буферизация на диске (store-and-forward),
        │  TLS mTLS, часы (NTP), пульс здоровья
        │  REST POST /ingest/telemetry:batch (push)  или MQTT
        ▼
[Ingestion (Go)]  ── валидация схемы/тега/единицы, дедупликация,
        │  идемпотентность, 202-ответ, запись в историк, публикация в Redis
        ▼
[Historian]  PostgreSQL + TimescaleDB (сырьё + агрегаты + retention)
        │
        ├── [Registry] Asset/Tag/Gateway/Profile — метаданные, уставки
        ├── [Alarms] состояния, рационализация, ack, шелвинг, аудит
        ├── [API v1] pull (история/агрегаты/latest/backfill/отчёты)
        └── [UI React] дашборд, тренды, оборудование-дерево, алермы, качество
```

Обоснование языков (решение по вопросу «хватит ли Python», утверждено 2026-07-31):

- **Платформа — Go, полностью.** Ядро/API, приём телеметрии, реестр, историк, алермы, аудит — всё на Go. Rust на уровне платформы исключён (обоснование в ARCHITECTURE_DECISIONS.md).
- **Почему не гибрид Python+Go:** продукт ставится на другие фабрики — один статический бинарь без рантайма/зависимостей на OT-серверах заказчика решает операционно; один язык на команду; общий Go-модуль канонической схемы исключает дрейф контракта между шлюзом и сервером.
- **Почему не Rust:** CAP — Level 3 мониторинг без контурных управлений; преимущества Rust (лагентность без GC, максимальная производительность) здесь не нужны, а цена (скорость разработки, кадры, экосистема OPC UA) — реальна. Rust — только точечно, для конкретного драйвера, после замера.
- **Миграция:** существующий Python-MVP переносится 1:1 с заморозкой контракта `backend/API.md`; контрактные тесты переписываются на Go без изменения семантики. Опционально — тонкий Python-микросервис только для аналитики (баланс, сверка с лабораторией), не как инфраструктура.

## 4. Универсальная модель датчиков (требование «много датчиков»)

1. **Реестр тегов** — единственная абстракция устройства. Никаких «зашитых» метрик в коде.
   Поля тега: `id`, `asset_id`, `name`, `unit`, `data_type (number|boolean|string|structured)`,
   `engineering_range`, `sampling_interval_seconds`, `criticality`, `calibration_due`,
   `alarm_limits`, `quality_policy`, `owner`, `active`.
2. **Реестр активов** — иерархия оборудования (дерево: завод → участок → агрегат → узел).
3. **Драйверы/адаптеры** — подключаемые модули протоколов (OPC UA, Modbus TCP, MQTT Sparkplug B, LIMS-файл/API). Адаптер возвращает каноническое сообщение. Добавление датчика = регистрация тега (+ новый драйвер при новом протоколе).
4. **Каноническое сообщение** (дополнить текущий контракт, версия остаётся `1.0`):

```json
{
  "schema_version": "1.0",
  "message_id": "uuid",
  "gateway_id": "gw-grinding-01",
  "source_sequence": 482119,
  "observed_at": "2026-07-31T08:15:30.125Z",
  "sent_at": "2026-07-31T08:15:31.008Z",
  "asset_id": "plant-a.grinding.mill-01",
  "tag_id": "plant-a.grinding.mill-01.motor_power",
  "value": 1245.7,
  "unit": "kW",
  "quality": "good",
  "profile_id": "ore-profile-2026-07-a"
}
```

   `value` — число, булев, строка или структура; тип диктует реестр тегов. Для
   структуры — подмассив подтегов с тем же контрактом. Служебные сообщения шлюза
   (онлайн/офлайн, загрузка буфера) — отдельный тип `gateway_event`.

## 5. API v1 (контракт; дополнения к текущему)

Все под `/api/v1`. Push — с машинной идентификацией, pull — с RBAC. Ошибки RFC 7807.

### 5.1 Push (устройство → сервер)
| Метод/путь | Поведение |
| --- | --- |
| `POST /ingest/telemetry` | одиночное каноническое сообщение; 202; `accepted/duplicate/rejected(code)` |
| `POST /ingest/telemetry:batch` | 1–500 сообщений, по-элементный результат в порядке входа, атомарно принятые |
| `POST /ingest/gateway_events` | онлайн/офлайн шлюза, объём буфера, задержки — для health |
| `POST /ingest/backfill:request` | запрос шлюзом недостающего диапазона (pull для шлюза) |

### 5.2 Pull (сервер → потребитель)
| Метод/путь | Поведение |
| --- | --- |
| `GET /telemetry` | история: `tag_id/asset_id/from/to/resolution/cursor/limit`; UTC; пагинация курсором; `resolution` — агрегированные ряды |
| `GET /telemetry/latest` | последнее значение по тегу/активу + качество + расчёт устаревания (staleness) |
| `GET /telemetry/aggregates` | avg/min/max/count по временным окнам (источник — TimescaleDB) |
| `GET /assets`, `GET /tags`, `GET /gateways` | реестры; без экспозиции адресов PLC/секретов |
| `GET /alarms`, `POST /alarms/{id}/acknowledgements` | история и подтверждение алермов (только человек, комментарий, аудит) |
| `GET /profiles`, `GET /profiles/{id}/versions` | профили руды и их версии |
| `GET /health` | liveness/readiness, включая число «устаревших» шлюзов без раскрытия внутренностей |

### 5.3 Реестры и конфигурация (с процессом согласования)
| Метод/путь | Поведение |
| --- | --- |
| `POST/PUT /registry/tags`, `POST/PUT /registry/assets` | запись через workflow с ролью и аудитом; без role — 403 |
| `POST /profiles`, `POST /profiles/{id}/versions`, `POST /profiles/{id}/approve` | создание/версия/согласование профиля руды |

## 6. Модель данных (реляционный слой)

- `Asset(id, name, area, parent_id, criticality, active, meta)`
- `Tag(id, asset_id, name, unit, data_type, engineering_min, engineering_max, sampling_interval_seconds, criticality, calibration_due, alarm_limits(JSON), quality_policy, owner, active)`
- `Gateway(id, name, area, protocol, last_seen_at, status, cert_fingerprint, config(JSON))`
- `TelemetryReading(gateway_id, message_id, source_sequence, observed_at, received_at, sent_at, asset_id, tag_id, value, value_text, value_bool, unit, quality, profile_id)` + unique `(gateway_id, message_id)` + индекс по `(tag_id, observed_at)` (должен быть гипотезой под TimescaleDB: гипертаблица по времени, retention, непрерывные агрегаты)
- `TelemetryAggregate(tag_id, window_start, window_end, avg, min, max, count, quality)` — из непрерывных агрегатов
- `Alarm(id, tag_id, state, severity, priority, observed_at, ack_by, ack_at, ack_comment, shelved_until, source_event_id)`; состояния: `normal | active_unacknowledged | active_acknowledged | returned_to_normal | shelved | suppressed_by_design`
- `Profile(id, name, ore_domain, version, effective_from, effective_to, params(JSON), limits(JSON), author, approved_by, approved_at, reason, status)` — аудит изменений в `AuditLog`
- `AuditLog(id, actor, action, target_type, target_id, before, after, at)`

Миграции: Alembic. Тесты: SQLite in-memory (как сейчас); нагрузочные — против TimescaleDB.

## 7. Алермы и события

- «Значение изменилось» — событие, **не** алерм.
- Каждый алерм: цель, последствие, действие оператора, приоритет, время реакции, предел/гистерезис/задержка, правила подавления, владелец, дата ревизии.
- Рационализация (ISA-18.2): документируется до включения уставок в профиль.
- Подтверждение (ack) никогда не меняет физический процесс и не стирает историю событий.
- Уставки живут в профилях/тегах, **не** в коде.

## 8. Edge Gateway (Go) — требования

- Один бинарь: подсистемы конфиг (YAML/ENV), протокольные драйверы, нормализация, **store-and-forward** (SQLite на борту/WAL), часы NTP + синхронизация, TLS mTLS к серверу, ротация ключей, локальные health/логи.
- Обработка обрыва: накопление → повторная доставка → приём по-элементных результатов → удаление только `accepted/duplicate`; `rejected` — в лог и регистр рассинхронизации.
- Pull-режим: драйвер-поллер опрашивает устройство, если оно не умеет push (это единственный случай «pull из поля», и он на шлюзе).
- Пульс `gateway_events` каждые N секунд.

## 9. UI (React) — требования

- Дашборд: оборудование-дерево, живые значения, тренды, алермы, статус связи, качество данных.
- Карточки по участкам из реестра (не из кода): участки/теги подтягиваются с `GET /assets`, `GET /tags`.
- Индикатор устаревания (staleness) и качества по тегу.
- Экран профилей руды и уставок (просмотр; изменение — через API с правами).
- Экраны алермов: список, подтверждение, шелвинг.
- Замена текущего «демо-набора метрик» на данные реестра; демо-режим (симулятор) — только в development.

## 10. Нефункциональные требования

- **Производительность (цель, проверить нагрузочным тестом):** приём ≥ 5 000 сообщений/с на узел; история запросов < 300 мс на окно 1 ч; приложение не теряет сообщения при корректном поведении шлюза (at-least-once + идемпотентность).
- **Отказоустойчивость:** Redis недоступен → приём всё равно пишет в историк (Redis — опциональный канал для UI); PostgreSQL недоступен → ingestion возвращает 503 и шлюз буферизует; повторная доставка безопасна.
- **Безопасность:** mTLS между шлюзом и сервером; RBAC (роли из `GET /access/roles`); никакого пути из интернета к полю; аудит всех изменений конфигурации; секреты только в защищённом хранилище; rate-limit на pull; отключение симулятора вне development.
- **Часы:** все метки UTC; допуск к времени в `observed_at` валидируется (допустимое опоздание/будущее).
- **Наблюдаемость:** метрики приложения (счётчики принятых/отклонённых/дубликатов, задержки, размеры буферов), структурированные логи, health.

## 11. Тестирование и критерии приёмки

- Контрактные тесты: валидное, дубликат, опоздавшее, невалидное, `bad/offline`, batch-границы, unknown_tag/unit_mismatch/asset_mismatch.
- Failure-mode тесты: обрыв Redis, обрыв PostgreSQL, разрыв между шлюзом и сервером (store-and-forward), перезапуск, повторная доставка.
- Свойства историка: дедупликация, порядок по тегу, агрегаты = корректны относительно сырых.
- UI-тесты: рендер из реестра, индикаторы качества/устаревания.
- **Ворота фазы 2 (edge-пилот):** сверка данных с прибором, восстановление после обрыва принято эксплуатацией.
- **Ворота фазы 3 (мониторинг):** рационализация алермов и приёмка операторами.
- **Ворота фазы 5 (прод):** FAT/SAT, ранбуки, план отката, go/no-go директора.

## 12. Бэклог спринтов (приоритизированный)

1. **S0 Инфраструктура:** Alembic, CI (lint+typecheck+тесты), структура сервисов, `.env` шаблоны.
2. **S1 Реестр и профили:** расширение моделей Asset/Tag (диапазоны, критичность, поверка, уставки), модели Profile/AuditLog, workflow согласования профилей, `GET/POST` registry API, удаление «зашитых» уставок из `schemas.py` в реестр/профили.
3. **S2 Канонический контракт + историк:** `sent_at`, булевы/строки/структуры, `gateway_events`, backfill-контракт; TimescaleDB гипертаблица, непрерывные агрегаты, retention; `GET /telemetry` с `resolution` и курсором.
4. **S3 Edge-шлюз (Go):** каркас, драйвер Modbus TCP, store-and-forward (SQLite), mTLS, пульс, backfill; потом драйвер OPC UA; MQTT Sparkplug B — по приоритету площадки.
5. **S4 Алермы:** модель состояний, рационализация через профили, ack/шелвинг, аудит, staleness в `/telemetry/latest`.
6. **S5 UI:** перевести дашборд на реестр (дерево оборудования, тренды, качество, устаревание), экраны профилей и алермов; убрать демо-метрики из фронтенда.
7. **S6 Безопасность и пилот:** RBAC end-to-end, аудит, rate-limit, бэкап/восстановление, нагрузочные тесты, threat model, пилот на некритичном участке.
8. **S7 Масштабирование и прод:** все участки, резервирование, наблюдаемость, ранбуки, FAT/SAT, go/no-go.

Каждый спринт заканчивается: зелёные тесты, обновлённый `backend/API.md`, миграции, демо для заказчика/металлургов.

## 13. Запреты для разработки

- Не писать логику под конкретный датчик/метрику в коде API или UI.
- Не использовать симулятор как источник в продакшене.
- Не записывать уставки и пороги в код (`schemas.py` THRESHOLDS — временная демо-заглушка, подлежит удалению в S1).
- Не добавлять «секретов» в репозиторий и логи.
- Не менять API-контракт без обновления `backend/API.md` и контрактных тестов.
